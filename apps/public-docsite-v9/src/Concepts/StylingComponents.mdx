## Styling components

Visit the **[Styling handbook](https://github.com/microsoft/fluentui/blob/master/docs/react-v9/contributing/rfcs/react-components/styles-handbook.md)** for a comprehensive styling guide, as this article only introduces basics to get you started quickly.

> If you need to build a custom component architecture (not just style existing components), see [Building custom components](?path=/docs/concepts-developer-building-custom-controls--docs).

### Getting started

Fluent UI React v9 components ship **plain, precompiled CSS**. Every component's rules live in one
cascade-layer family:

```css
@layer fui.theme, fui.base, fui.components, fui.components.l1, fui.components.l2, fui.components.l3,
  fui.components.l4, fui.components.l5, fui.utilities;
```

That single fact is what makes styling simple: **the CSS cascade compares layers before it looks at
specificity, and unlayered CSS beats every layer.** So your own stylesheet wins over Fluent's rules by
default — no specificity war, no `!important`, no ordering tricks.

Write ordinary CSS (or a CSS Module, or Tailwind, or whatever your app already uses) and pass the class
to the component:

```css
/* MyForm.module.css */
.submit {
  background-color: var(--colorBrandBackground);
  border-radius: 9999px;
}
```

```jsx
import { Button } from '@fluentui/react-components';

import styles from './MyForm.module.css';

function MyForm() {
  return (
    <Button appearance="primary" className={styles.submit}>
      Save
    </Button>
  );
}
```

> ⚠ Fluent's component CSS references theme-level custom properties that something has to emit once per
> document. If you have not already, import `@fluentui/react-tailwind-theme/styles.css` at your app root —
> see [Quick start](?path=/docs/concepts-developer-quick-start--docs). Without it, spacing collapses to `0px`.

### Styling a component's internals — slot `className` props

`className` on the component styles its **root**. Every other part of a component is a **slot**, and every
slot takes its own `className`:

```jsx
import { Button } from '@fluentui/react-components';
import { CallEndRegular } from '@fluentui/react-icons';

import styles from './MyForm.module.css';

<Button className={styles.button} icon={{ className: styles.buttonIcon, children: <CallEndRegular /> }} />;
```

Slot `className` props are the **only** supported way to reach a component's internals. The classes Fluent
puts on its own internal elements are hashed CSS-Module identifiers (`fuicm-button-root-a1b2c3`) and are
deliberately not addressable from outside the module that declares them.

> The `*ClassNames` constants (`buttonClassNames`, `textClassNames`, …) are still exported so existing code
> compiles, but they are `@deprecated` **for styling**: they no longer describe the BEM classes v9 used to
> render. See [Component identity classes](#component-identity-classes) below for what `root` holds now.

### Composing class names

Class names are inert identifiers, so combine them with any string-joining helper you like. Fluent's own
components use [`clsx`](https://www.npmjs.com/package/clsx):

```jsx
import { clsx } from 'clsx';

import styles from './MyForm.module.css';

function Component(props) {
  return <div className={clsx(styles.root, props.primary && styles.primary, props.className)} />;
}
```

There is no merge or de-duplication step to reason about, and **argument order carries no cascade meaning** —
every conflict between the rules behind two class names is settled by the cascade (layer first, then
specificity, then source order). Put the consumer's `props.className` last by convention, not because the
position decides anything.

> This is the one behavioural difference from v9's earlier `mergeClasses()`, where argument order _did_ decide
> the winner. If you are porting code that relied on that, the winner is now decided by where the competing
> rules live — see [Which rule wins](#which-rule-wins).

### Mapping props and state to styles

Two mechanisms, and the choice matters:

- **A class**, when the variation is purely a look.
- **A `data-*` attribute**, when the variation is a piece of _state_ another element may need to react to.

Fluent's own components follow the same rule: `<Text size={400} />` renders `data-size="400"` on its root,
and Text's stylesheet selects it. Your CSS can too:

```css
.row[data-density='compact'] {
  padding-block: 2px;
}
```

```jsx
<div className={styles.row} data-density={density} />
```

### Which rule wins

In order, the cascade asks:

1. **Layer.** Unlayered author CSS beats every `@layer`. Within the `fui` family, later layers beat earlier
   ones, so `fui.components.l4` beats `fui.components.l1`.
2. **Specificity** — only between rules in the _same_ layer. Fluent's selectors are `:where()`-flattened, so
   most of them sit at a single class's specificity.
3. **Source order** — only between rules of equal layer and specificity.

Which gives three ways to override a Fluent style, in order of preference:

| You are…                               | Do this                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------- |
| a plain-CSS / CSS-Modules app          | nothing special — your unlayered rules already win                         |
| a Tailwind v4 app                      | declare the `fui` layers before importing Tailwind (see below)             |
| authoring app-wide / page-level layers | author into `fui.components.l3` (app-global), `l4` (page), `l5` (one-offs) |

Levels `l3`–`l5` are deliberately left empty by the library and are yours. They beat every library rule and
still lose to your unlayered CSS:

```css
@layer fui.components.l3 {
  .my-design-layer-button {
    border-radius: 0;
  }
}
```

Tailwind consumers who want their own utilities to outrank Fluent component styles declare the layer order
first — cascade layer order is first-appearance:

```css
@layer fui.theme, fui.base, fui.components, fui.utilities;
@import 'tailwindcss';
```

### Applying theme to styles

No matter what theme is used, the component styles are always the same. The only way to change component
styling globally is through theme tokens, which are CSS custom properties. Reference them directly in CSS:

```css
.root {
  display: flex;
  color: var(--colorNeutralForeground3);
}
```

`FluentProvider` sets those custom properties on its own element and updates them when the theme changes, so
only the variables change — the rules never do. That is also why per-provider and nested-provider theming work
unchanged.

If you are generating styles from JavaScript and need the token _names_, the `tokens` object still exports
them:

```js
import { tokens } from '@fluentui/react-components';

const style = { color: tokens.colorNeutralForeground3 }; // → 'var(--colorNeutralForeground3)'
```

For more details, see [Theming](?path=/docs/concepts-developer-theming--docs).

### Component identity classes

Each component's root carries one **named group marker** — `group/fui-button`, `group/fui-text`,
`group/fui-message-bar` — and that marker is what `<component>ClassNames.root` holds today. It is the
component's public identity class: usable as a selector, and (for Tailwind consumers) as a `group-*` variant
target.

The `/` is legal inside a class _token_ but terminates the name inside a _selector_, so string-concatenating
it produces an invalid selector. Use `fuiSelector()`:

```js
import { buttonClassNames, fuiSelector } from '@fluentui/react-components';

// buttonClassNames.root === 'group/fui-button'
document.querySelectorAll(fuiSelector(buttonClassNames.root));
```

Token-taking APIs (`classList.contains`, `getElementsByClassName`) need no escaping.

### Incorrect usages

```css
/* ❌ Hardcoded colors are not theme-able. Always use a token custom property. */
.root {
  color: #c50f1f;
}

/* ✅ */
.root {
  color: var(--colorPaletteRedForeground1);
}
```

```css
/* ❌ !important is never necessary — layers already decide this. It also removes the app's
      last escape hatch, since !important reverses layer order. */
.root {
  display: flex !important;
}
```

```jsx
/* ❌ Reaching for a component's internal class name. Hashed, unstable, not public API. */
<div className="fuicm-button-icon-8f2a11" />

/* ✅ Use the slot's className prop. */
<Button icon={{ className: styles.icon }} />
```

### Debugging styles

Component styles are real stylesheet rules, so the browser's own DevTools are the whole toolchain: select the
element and read **Styles** top to bottom. Chrome and Firefox both label the `@layer` each rule came from, and
struck-through declarations show you exactly which layer won.

If a rule you wrote is losing, check the layer label first — a rule inside `fui.components.l1` losing to one in
`fui.components.l4` is working as designed.

### Still using `makeStyles`?

`makeStyles`, `makeResetStyles`, `mergeClasses` and `shorthands` are still exported from
`@fluentui/react-components`, so existing app code keeps working. They come from
[Griffel](https://griffel.js.org), which the library used to author its own styles with and no longer does.

They remain a supported escape hatch, with one thing worth knowing: Griffel injects its rules **unlayered**, so
a class from `makeStyles` beats every Fluent layer — your existing overrides still win. For new code, prefer
plain CSS or CSS Modules; you get the same result with no runtime, no build transform, and DevTools that can
explain the outcome.
