# ChoiceGroup to RadioGroup Migration

See the [v8 component migration inventory](/docs/concepts-migration-from-v8-component-mapping--docs).

## Overview

Use [RadioGroup](/docs/components-radiogroup--docs) together with `Radio` for Fluent UI v9 migrations from `ChoiceGroup`. The structural shift is larger than a simple rename: `ChoiceGroup` accepts `options` data and owns its visible label, while v9 moves visible labeling and validation UI to [Field](/docs/components-field--docs) and expresses each option as an explicit `Radio` child.

The largest migration risks are option composition, controlled state, and accessibility wiring. `selectedKey` or `defaultSelectedKey` become `value` or `defaultValue`, change handlers now read `data.value`, and custom rendering moves from render callbacks into ordinary JSX and slot content.

## Component mapping

| v8 scenario                                    | v9 destination                            | Notes                                                                                                                                     |
| ---------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Standard `ChoiceGroup` with a visible label    | `Field` plus `RadioGroup` plus `Radio`    | `Field` restores the visible label, hint, validation message, and required indicator that are not built into `RadioGroup`.                |
| External label via `label` or `ariaLabelledBy` | `RadioGroup` plus explicit ARIA labeling  | When `Field` is not the right shell, supply `aria-labelledby` or `aria-label` directly on the `RadioGroup`.                               |
| Horizontal options via `styles.flexContainer`  | `RadioGroup layout="horizontal"`          | Layout is a first-class prop in v9, and `horizontal-stacked` is an additional layout with labels below the indicators.                    |
| Custom option render callbacks                 | `Radio` label slot and composed children  | Replace `onRenderField` and `onRenderLabel` with regular React composition around `Radio` or custom JSX passed to the `label` slot.       |
| Per-option icon or image props                 | Custom label content or composed children | V9 does not expose dedicated `iconProps`, `imageSrc`, `selectedImageSrc`, or `imageSize` props on `Radio`; render those visuals yourself. |

## What changed

V8 `ChoiceGroup` stores option metadata in `options`, using each `key` as both the stable identifier and the selected value. In v9 you render `Radio` children directly, and the selected option is tracked by the `RadioGroup` `value` or `defaultValue` matching each child's `value`. Because `RadioGroupProps.value` is a string, any numeric v8 keys should be normalized to strings during migration.

Labeling and validation also move. `ChoiceGroup` owns its `label` prop, while `RadioGroup` expects surrounding form-field UI to come from `Field` or from explicit `aria-labelledby` or `aria-label` props. `RadioGroup` adds a built-in `layout` prop with `vertical`, `horizontal`, and `horizontal-stacked` values, so the old `styles.flexContainer` pattern becomes a direct API rather than a layout override.

V8 callbacks receive the selected `IChoiceGroupOption`, but v9 `RadioGroup` change handlers receive a `RadioGroupOnChangeData` object and you read the next selection from `data.value`. Option customization follows the same pattern: render callbacks are replaced by slot content and normal React composition, with `Radio`'s `label` slot handling most text, subtext, or decorative visual scenarios.

## Architecture and behavior

Treat `Field` as the form-field shell and `RadioGroup` as the mutually exclusive selection control. `Field` owns the visible label, hint text, validation message, required indicator, and `aria-*` relationships for the grouped radios; `RadioGroup` owns the current selection, shared `name`, `layout`, and propagation of `disabled`, `required`, and `aria-describedby` to its child radios.

Controlled state is group-owned in v9. Instead of marking an individual option `checked`, set `value` on `RadioGroup` and update it from `onChange`. Uncontrolled state follows the same pattern with `defaultValue`. Each `Radio` still supports native input props such as `onFocus` and `onBlur`, but selection should be driven by the group so the browser can preserve mutual exclusivity and arrow-key behavior.

Custom layouts are also more explicit. Use `layout="horizontal"` when the v8 control depended on `styles.flexContainer`, and use `layout="horizontal-stacked"` when you want the labels to sit below each indicator. For option visuals beyond plain text, pass JSX to the `label` slot or compose wrappers around `Radio` instead of relying on `onRenderField`.

## Prop mapping

### `IChoiceGroupProps`

| v8 prop              | v9 equivalent                               | Status  | Migration notes                                                                                                                           |
| -------------------- | ------------------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `componentRef`       | `ref` on `RadioGroup`                       | Partial | The v9 ref targets the root `<div>` only; the v8 `IChoiceGroup.checkedOption` and `focus()` instance API do not have direct replacements. |
| `options`            | `RadioGroup` children                       | Use     | Render one `Radio` per option instead of passing a data array.                                                                            |
| `defaultSelectedKey` | `defaultValue`                              | Use     | Normalize numeric keys to strings because `RadioGroupProps.defaultValue` is `string`.                                                     |
| `selectedKey`        | `value`                                     | Use     | Controlled selection now lives on the group. Normalize numeric keys to strings before comparing them to child `Radio value` props.        |
| `onChange`           | `onChange(event, data)`                     | Use     | Read the newly selected option from `data.value` instead of from an `IChoiceGroupOption` callback argument.                               |
| `label`              | `Field label` or explicit `aria-labelledby` | Compose | Use `Field` for the visible group label and validation UI, or wire your own visible label to `RadioGroup` with `aria-labelledby`.         |
| `theme`              | `FluentProvider`                            | Use     | Theming moves to provider context instead of a per-instance prop.                                                                         |
| `styles`             | `layout`, `className`, and Griffel styles   | Compose | Use `layout="horizontal"` for the common flex-row pattern, and use Griffel classes for slot-level layout or visual customization.         |
| `ariaLabelledBy`     | `aria-labelledby`                           | Use     | The v8 custom prop becomes the intrinsic HTML attribute on `RadioGroup`.                                                                  |

### `IChoiceGroupOption` and `IChoiceGroupOptionProps`

| v8 prop            | v9 equivalent                               | Status      | Migration notes                                                                                                                              |
| ------------------ | ------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `key`              | `Radio value`                               | Use         | The option identifier becomes the child's `value`; keep a React `key` only when mapping arrays to `Radio` children.                          |
| `text`             | `label`                                     | Use         | `Radio` `label` can be a string, JSX, or a shorthand object with slot props.                                                                 |
| `onRenderField`    | Compose JSX around `Radio`                  | Compose     | Render the surrounding option layout directly with normal React composition when the control needs extra visuals or wrappers.                |
| `onRenderLabel`    | `label` slot content                        | Compose     | Put custom markup directly in the `label` slot instead of returning it from a callback.                                                      |
| `iconProps`        | Custom label content                        | Compose     | Render the icon inside the `label` slot or beside the `Radio` with your own JSX.                                                             |
| `imageSrc`         | Custom label content                        | Compose     | Render images manually in the label or surrounding layout.                                                                                   |
| `imageAlt`         | Custom image `alt` text                     | Compose     | Preserve accessible image text on the custom image you render.                                                                               |
| `selectedImageSrc` | Controlled custom composition               | Compose     | Branch your custom option visuals from `RadioGroup value` when the selected state changes; there is no direct `selectedImageSrc` prop in v9. |
| `imageSize`        | Griffel styles on custom content            | Compose     | Size custom images or wrappers with regular classes instead of a dedicated prop.                                                             |
| `disabled`         | `disabled`                                  | Use         | You can disable the whole group from `RadioGroup` or a single choice from the `Radio`.                                                       |
| `id`               | `id`                                        | Use         | `Radio` accepts the native input `id` directly.                                                                                              |
| `labelId`          | `label={{ id: '...' }}` or custom label JSX | Use         | Pass an `id` through the `label` slot props when another element needs to reference the visible option label.                                |
| `ariaLabel`        | `aria-label`                                | Use         | The native attribute is forwarded to the underlying radio input.                                                                             |
| `styles`           | `className` on `Radio` or `label` slot      | Use         | Style the radio root with `className` and the visible label with `label={{ className: ... }}`.                                               |
| `itemKey`          | `Radio value`                               | Use         | `itemKey` duplicates the option identifier in v8; in v9 the `value` prop is the single source of truth.                                      |
| `checked`          | `RadioGroup value` or `defaultValue`        | Use         | Drive selection from the group instead of setting an individual radio as checked.                                                            |
| `onChange`         | `RadioGroup onChange` or `Radio onChange`   | Use         | Prefer the group callback for migrations so every selection change reports the latest `data.value`.                                          |
| `onFocus`          | `onFocus` on `Radio`                        | Use         | Focus handlers stay native.                                                                                                                  |
| `onBlur`           | `onBlur` on `Radio`                         | Use         | Blur handlers stay native.                                                                                                                   |
| `focused`          | No direct prop                              | Unsupported | V9 does not expose a prop that forces the focused visual state on a radio.                                                                   |
| `theme`            | `FluentProvider`                            | Use         | Theme context comes from the provider.                                                                                                       |
| `required`         | `RadioGroup required` and `Field required`  | Use         | `RadioGroup required` propagates the native `required` state, while `Field required` adds the visible required indicator.                    |
| `name`             | `RadioGroup name`                           | Use         | `RadioGroup` applies one shared `name` to every child radio automatically, or you can provide it explicitly at the group level.              |

## Styling and theming

Use `RadioGroup`'s `layout` prop first, then add Griffel classes for custom visual treatment. Horizontal v8 groups that only needed `styles.flexContainer` usually collapse to `layout="horizontal"`, while option-level customizations move to `Radio className` or `label={{ className: ... }}`. When a migration needs image cards or richer wrappers, compose your own surrounding elements and style them with design tokens.

Per-instance `theme` props do not carry forward. Use `FluentProvider` for theme selection, and prefer design tokens over copied v8 color values when recreating custom option visuals.

## Accessibility

`RadioGroup` needs an accessible group label in addition to the visible labels for each `Radio`. The recommended migration pattern is `Field`, which sets `aria-labelledby` for the group and merges hint or validation message IDs into `aria-describedby`. If you do not use `Field`, supply `aria-labelledby` or `aria-label` on `RadioGroup` yourself.

Each `Radio` still needs a visible label, usually through the `label` prop. Custom label JSX is supported, but interactive elements should not be placed inside the label content because the label click target is how the radio is selected. For extra per-option description, use additional text plus `aria-describedby` on the relevant `Radio` instead of hiding important content in a purely visual wrapper.

Keyboard behavior remains the standard radio-group pattern: the group is one tab stop, and arrow keys both move focus and change selection. That behavior depends on keeping radios inside a `RadioGroup` so they share a `name` and role wiring.

## Unsupported scenarios and known gaps

There is no direct v9 replacement for the v8 `IChoiceGroup` instance surface exposed through `componentRef`, so code that depended on `checkedOption` or `focus()` needs to manage selection state or focus targets explicitly.

`RadioGroup` and `Radio` also are not the right migration target inside composite widgets such as `Toolbar`, `Menu`, `Tree`, or `Listbox`. Use `ToolbarRadioGroup` or the component-specific single-selection semantics instead of nesting radios into those controls.

The old `focused` prop and image-specific option props (`selectedImageSrc`, `imageSrc`, `imageSize`) do not map to dedicated `Radio` APIs. Those scenarios require custom composition and state-driven visuals rather than a one-prop replacement.
