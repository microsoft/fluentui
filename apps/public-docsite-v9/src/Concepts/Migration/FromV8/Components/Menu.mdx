# ContextualMenu to Menu Migration

See the [v8 component migration inventory](/docs/concepts-migration-from-v8-component-mapping--docs).

## Overview

Use [Menu](/docs/components-menu-menu--docs) when migrating `ContextualMenu` scenarios to Fluent UI v9. The largest shift is architectural: v8 centralizes menu structure in an `items` array and optional render callbacks, while v9 uses explicit child components such as `MenuTrigger`, `MenuPopover`, `MenuList`, `MenuItem`, `MenuItemCheckbox`, `MenuGroup`, and nested `Menu` instances.

Expect to rewrite item definitions, open-state control, and positioning. V9 no longer exposes callout beaks or FocusZone customization on `Menu`, but it adds clearer compound structure, built-in submenu composition, and a distinct `MenuItemRadio` pattern for single-select menu groups.

## Component mapping

| v8 scenario                                                        | v9 destination                                                    | Notes                                                                                                                             |
| ------------------------------------------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Standalone `ContextualMenu`                                        | `Menu` plus `MenuPopover` plus `MenuList`                         | Use a triggerless `Menu` only when you must anchor to a custom target; otherwise prefer `MenuTrigger` for built-in accessibility. |
| `Button` with `menuProps` or a launch button plus `ContextualMenu` | `Menu` plus `MenuTrigger` plus a trigger child such as `Button`   | The trigger owns `aria-haspopup`, `aria-expanded`, keyboard open, and focus restoration.                                          |
| `itemType: Divider`                                                | `MenuDivider`                                                     | Dividers are their own component instead of a sentinel item entry.                                                                |
| `itemType: Header` or `itemType: Section`                          | `MenuGroupHeader` and `MenuGroup`                                 | Group structure is explicit in the child tree.                                                                                    |
| `canCheck` plus `checked` items                                    | `MenuItemCheckbox` with `checkedValues` or `defaultCheckedValues` | Selection state moves from per-item booleans to menu-managed checked values.                                                      |
| `subMenuProps`                                                     | Nested `Menu`                                                     | Each submenu is its own `Menu` with a `MenuItem` trigger inside the parent `MenuList`.                                            |
| `href` menu items                                                  | `MenuItemLink`                                                    | Use the link-specific item component instead of mixing button and anchor behavior in one item shape.                              |
| Single-select menu groups                                          | `MenuItemRadio`                                                   | This is a new v9 capability, not a direct v8 `ContextualMenu` item mapping.                                                       |
| Split menu actions                                                 | `MenuSplitGroup` plus nested `MenuTrigger`                        | Split actions still work, but the trigger and primary action are composed explicitly.                                             |

## What changed

`ContextualMenu` item arrays become declarative children. Instead of feeding `items`, `sectionProps`, and `subMenuProps` into one data shape, you author the menu tree directly with `MenuList`, `MenuGroup`, `MenuGroupHeader`, `MenuDivider`, `MenuItem`, and nested `Menu` components.

Item variants are also separate components now. Checkbox-like entries use `MenuItemCheckbox`, submenu triggers are normal `MenuItem` children wrapped by nested `Menu`, link navigation moves to `MenuItemLink`, and v9 adds `MenuItemRadio` as a new capability for single-select groups.

Visibility and dismissal are controlled through `open`, `defaultOpen`, and `onOpenChange` instead of `hidden`, `onDismiss`, `onMenuOpened`, and `onMenuDismissed`. Positioning moves from `target`, `directionalHint`, and `calloutProps` into trigger composition and the `positioning` prop. Render callbacks such as `onRender`, `onRenderContent`, `onRenderMenuList`, and `onRenderSubMenu` are replaced by slots, normal JSX children, or direct composition of the compound menu parts.

## Architecture and behavior

Treat `Menu` as the state container and `MenuTrigger`, `MenuPopover`, and `MenuList` as the structural shell around the items. `MenuTrigger` clones a single child and injects the button semantics needed to open the menu, while `MenuPopover` and `MenuList` own popup rendering and keyboard navigation.

When the old menu was conditionally shown with `hidden`, migrate that logic to `open` and `onOpenChange`. The callback supplies `data.open` plus a `data.type` reason such as `menuTriggerClick`, `menuItemClick`, or `clickOutside`, so you can mirror v8 dismissal logic without inspecting DOM events manually. Nested menus are separate `Menu` components inside the parent `MenuList`, which keeps submenu behavior, hover delay, and keyboard semantics local to each branch.

## Styling and theming

Move v8 `styles`, `style`, and class-name factories to Griffel classes applied to the menu slots you actually render. In practice that usually means a class for `MenuPopover`, `MenuList`, or specific item slots such as `icon`, `secondaryContent`, or `submenuIndicator`. Keep spacing, color, and typography aligned with Fluent v9 design tokens.

Theme changes move to `FluentProvider`. Do not pass per-instance `theme` props to the menu tree; instead, wrap the relevant subtree and let `Menu`, `MenuPopover`, and the item components consume the shared theme context.

## Accessibility

Prefer `MenuTrigger` whenever the menu is launched by an interactive control. It wires `aria-haspopup`, `aria-expanded`, keyboard open behavior, and focus restoration for you. Only use a triggerless `Menu` when you truly need a custom anchor, and then supply your own accessible trigger semantics and focus restoration.

Use `MenuGroup` with `MenuGroupHeader` for sectioned content so screen readers get meaningful group labeling. `MenuList` owns keyboard navigation, so the old FocusZone escape hatches are intentionally absent. When you compose split actions or submenu triggers, give the submenu trigger an explicit `aria-label` if its visible text is ambiguous.

## Unsupported scenarios and known gaps

There is no v9 equivalent for the v8 callout beak props such as `beakWidth` and `isBeakVisible`, so menus no longer render a beak. `shouldUpdateWhenHidden` also has no supported replacement; if you need a reusable popup, keep the menu state outside the component tree and reopen it with `open`.

`focusZoneAs`, `focusZoneProps`, `contextualMenuItemAs`, `onRenderContextualMenuItem`, and `keytipProps` do not map to stable v9 menu props. Rebuild those scenarios with the explicit compound components, or move the customization outside the menu when the behavior is no longer a good fit for the v9 control.
