# Drawer Migration

See the [v8 component migration inventory](/docs/concepts-migration-from-v8-component-mapping--docs).

## Overview

Use [Drawer](/docs/components-drawer--docs) when a v8 `Panel` provides supplementary editing, review, or navigation content beside the main page. The first migration decision is no longer a `PanelType`; it is whether the surface should remain an overlay (`OverlayDrawer`) or become part of the page layout (`InlineDrawer`). Overlay drawers preserve the dialog-like experience, while inline drawers are for always-available or adjacent content that should push sibling layout instead of floating above it.

The highest migration risk is assuming there is still one catch-all root component. V8 `Panel` centralizes visibility, title text, close behavior, footer rendering, and responsive sizing on one API. V9 splits those concerns across `OverlayDrawer` or `InlineDrawer`, `DrawerHeader`, `DrawerHeaderNavigation`, `DrawerHeaderTitle`, `DrawerBody`, and `DrawerFooter`, so each scenario should be re-authored deliberately instead of translated prop-for-prop.

## Component mapping

| v8 scenario                                                  | v9 destination                                                                           | Notes                                                                                                   |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Standard blocking `Panel` for editing or review              | `OverlayDrawer` + `DrawerHeader` + `DrawerHeaderTitle` + `DrawerBody`                    | Keep the modal overlay model and translate dismissal to controlled `open` state.                        |
| Non-blocking or modeless `Panel`                             | `OverlayDrawer modalType="non-modal"`                                                    | The page stays interactive, but the surface is still an overlay and needs focus restoration.            |
| Embedded supplemental content that should share page layout  | `InlineDrawer` + `DrawerHeader` + `DrawerBody`                                           | This is not the same as `isBlocking={false}`; it becomes a layout primitive instead of a modal surface. |
| `headerText`, `onRenderHeader`, `onRenderNavigation`, footer | `DrawerHeaderNavigation`, `DrawerHeaderTitle`, `DrawerBody`, and `DrawerFooter` children | V9 moves header, navigation, body, and footer content from render props into explicit children.         |
| `PanelType` sizing and anchoring                             | `position` + `size`, with optional custom surface styling                                | Near/far anchoring becomes `start` or `end`; full-screen behavior maps to `size="full"`.                |

## What changed

V8 `Panel` is an opinionated overlay with one root API. V9 `Drawer` is a family of primitives. Before translating individual props, pick `OverlayDrawer` when the content should still behave like a dialog surface or `InlineDrawer` when the content should live beside the rest of the page.

State and dismissal change shape too. `isOpen` becomes `open`, and overlay dismissal moves from `onDismiss` to `onOpenChange(event, data)`. The callback reports both the next `data.open` value and the interaction type, so light-dismiss logic should branch on `data.type === 'backdropClick'` instead of relying on a dedicated `onLightDismissClick` prop. `InlineDrawer` keeps the simpler `open` boolean without any dialog dismissal callback because there is no backdrop or `Escape` contract to translate.

Structure is now explicit. Instead of `headerText`, `hasCloseButton`, `onRenderHeader`, `onRenderNavigation`, and `onRenderFooterContent` all configuring one root panel, v9 authors the navigation, title, body, and footer as real children. That makes the migrated layout more obvious, but it also means every customized v8 region must be rebuilt intentionally.

## Architecture and behavior

Start each migration by choosing the surface boundary. `OverlayDrawer` uses dialog semantics under the hood, so it participates in modal or non-modal focus management, reports `onOpenChange`, and can render into a custom `mountNode`. `InlineDrawer` skips dialog semantics entirely and simply adds or removes layout content according to `open`.

That split affects behavior more than the rename from Panel to Drawer. A v8 non-blocking panel still floats in a portal-like layer, while an inline drawer consumes space next to the main content. Conversely, a modal overlay drawer keeps overlay dismissal and `Escape` handling, which means product teams should decide whether users still need the page to go inert or whether `modalType="non-modal"` is the better match.

Composition is the second architectural shift. `DrawerHeaderNavigation` carries toolbar-like controls, `DrawerHeaderTitle` owns the visible heading and optional close action, `DrawerBody` contains the scrollable content region, and `DrawerFooter` carries secondary and primary actions. Styling also happens per slot, so body spacing, footer alignment, and header affordances no longer share one monolithic `styles` bag.

## Prop mapping

| v8 prop or pattern      | v9 equivalent                                                                                | Status  | Migration notes                                                                                                    |
| ----------------------- | -------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------ |
| `isOpen`                | `open`                                                                                       | Replace | Both overlay and inline drawers use positive open state.                                                           |
| `onDismiss`             | `onOpenChange(event, data)` on `OverlayDrawer`; explicit `setOpen(false)` for `InlineDrawer` | Replace | Overlay drawers report `data.open` and `data.type`; inline drawers do not expose dialog dismissal semantics.       |
| `type`                  | `position` + `size`                                                                          | Replace | Translate near/far anchoring to `start` or `end`, then choose a supported size deliberately.                       |
| `headerText`            | `DrawerHeaderTitle` children                                                                 | Replace | Title text becomes explicit JSX in the heading slot instead of a root prop.                                        |
| `hasCloseButton`        | `DrawerHeaderTitle action` with a `Button`                                                   | Replace | Compose the close affordance explicitly and give the button its own `aria-label`.                                  |
| `isBlocking`            | `modalType="modal"` or `modalType="non-modal"` on `OverlayDrawer`                            | Replace | Blocking and page interactivity are now a modal-type choice instead of a boolean on every panel.                   |
| `isLightDismiss`        | Modal `OverlayDrawer` dismissal through `onOpenChange`                                       | Partial | Overlay drawers still support backdrop dismissal, but inline drawers do not because there is no backdrop.          |
| `onLightDismissClick`   | Branch on `data.type === 'backdropClick'` inside `onOpenChange`                              | Replace | There is no dedicated light-dismiss callback in v9.                                                                |
| `onRenderHeader`        | `DrawerHeaderTitle` plus ordinary JSX                                                        | Compose | Rebuild the header directly in JSX and keep the heading associated with the overlay surface.                       |
| `onRenderNavigation`    | `DrawerHeaderNavigation`                                                                     | Replace | Navigation content becomes a dedicated child region instead of a render callback.                                  |
| `onRenderFooterContent` | `DrawerFooter` children                                                                      | Replace | Footer actions become explicit children and can be aligned with normal layout techniques.                          |
| `customWidth`           | `className` or `style` width on `OverlayDrawer`                                              | Partial | There is no `PanelType.custom`; keep custom widths deliberate and verify responsive behavior separately.           |
| `closeButtonAriaLabel`  | `aria-label` on the close `Button` in `DrawerHeaderTitle action`                             | Replace | The close button is authored by you, so its accessible name is no longer generated from one root prop.             |
| `layerProps`            | `mountNode` on `OverlayDrawer`                                                               | Partial | V9 keeps mount-node targeting, but it drops the broader v8 layer configuration bag.                                |
| `styles`                | Slot `className` props with Griffel and Fluent design tokens                                 | Replace | Style the overlay surface, header, body, and footer individually instead of extending one monolithic style object. |
| `theme`                 | `FluentProvider`                                                                             | Replace | Theme context comes from the provider, not a per-instance component prop.                                          |

## Styling and theming

V8 `Panel` styling often starts with one `styles` object or a `theme` prop on the root component. V9 drawers are styled slot by slot: use `className` on `OverlayDrawer` or `InlineDrawer` for the surface, `DrawerHeaderNavigation` and `DrawerHeaderTitle` for header affordances, `DrawerBody` for spacing and typography, and `DrawerFooter` for action alignment. This is a good time to break broad panel overrides into smaller, purpose-specific Griffel classes.

Keep those styles token-driven. Use Fluent design tokens for spacing, border radii, color, and typography so the migrated drawer follows the active `FluentProvider` theme automatically. When a v8 panel relied on `customWidth`, prefer the built-in `size` values first and only reach for an explicit surface width when the product requirement still demands it.

## Accessibility

Overlay drawers still need an accessible title and close affordance, but you author both pieces yourself. `DrawerHeaderTitle` provides the heading content that labels the surface, so keep a visible heading or provide equivalent `aria-labelledby` or `aria-label` wiring when you diverge from the default structure. Any custom close button should keep the accessible name that used to come from `closeButtonAriaLabel`.

Focus behavior is different enough to test explicitly during migration. Overlay drawers use dialog semantics, so modal drawers trap focus, non-modal drawers leave the page interactive, and both patterns should restore focus with `useRestoreFocusTarget()` and `useRestoreFocusSource()` when the trigger lives outside the drawer tree. Inline drawers stay in document flow, do not close on `Escape`, and should only be chosen when that persistent, layout-based behavior is appropriate.

Because `modalType="non-modal"` still renders an overlay surface, screen-reader and keyboard users should understand whether the surface is supplemental or blocking. Re-test `Escape`, close-button labeling, and any custom navigation controls after moving the content out of v8 render props.

## Unsupported scenarios and known gaps

MC-4: `PanelType.large`, `PanelType.largeFixed`, `PanelType.extraLarge`, `PanelType.custom`, and `PanelType.customNear` do not map one-to-one. Use the nearest supported `size`, reserve `customWidth`-style overrides for deliberate exceptions, and treat the v9 `bottom` drawer position as a new capability rather than a Panel migration target.

MC-5: There is no catch-all replacement for `layerProps`, `focusTrapZoneProps`, or `onLightDismissClick`. `OverlayDrawer` keeps `mountNode`, `modalType`, `inertTrapFocus`, and `onOpenChange`, while `InlineDrawer` omits backdrop and `Escape` dismissal behavior entirely.
