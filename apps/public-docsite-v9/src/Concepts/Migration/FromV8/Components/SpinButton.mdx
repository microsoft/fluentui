# SpinButton Migration

See the [v8 component migration inventory](/docs/concepts-migration-from-v8-component-mapping--docs).

## Overview

Use [SpinButton](/docs/components-spinbutton--docs) for Fluent UI v9 numeric stepper scenarios. The largest migration change is the value model: v8 `SpinButton` stores committed values as strings and often mixes formatting into that string, while v9 keeps the source of truth numeric in `value` or `defaultValue` and optionally renders a separate `displayValue`.

V9 also separates form-field layout from the control. When the v8 component rendered its own label, horizontal label position, hint text, or validation message, wrap the v9 `SpinButton` in [Field](/docs/components-field--docs) so the visible label and `aria-*` wiring stay correct.

## Component mapping

| v8 scenario                                    | v9 destination                                           | Notes                                                                                                                                |
| ---------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Standard labeled `SpinButton`                  | `Field` plus `SpinButton`                                | `Field` restores the visible label, hint, validation message, required indicator, and optional horizontal label layout.              |
| Inline or label-less spinbutton                | `SpinButton` with `aria-label` or `aria-labelledby`      | Keep an explicit accessible name whenever the control is not wrapped in `Field`.                                                     |
| Formatted string values with custom callbacks  | Controlled `SpinButton` with `value` plus `displayValue` | Parse `data.displayValue` when users type text, then store the numeric result in `value` and the formatted string in `displayValue`. |
| Custom increment and decrement button labeling | `SpinButton` slot props                                  | Override the built-in button names with `incrementButton={{ 'aria-label': '...' }}` and `decrementButton={{ 'aria-label': '...' }}`. |

## What changed

V8 `SpinButton` mixes two concepts into one string value: the committed numeric state and whatever formatted text is shown to the user. That is why v8 callback shapes such as `onIncrement`, `onDecrement`, and `onValidate` all work with strings. In v9, `SpinButtonProps.value` and `defaultValue` are numeric, and formatted text moves to the optional controlled `displayValue` prop.

The event model also changes. V8 `onChange` reports an optional `newValue` string after stepping or validation. V9 consolidates typing, stepping, and keyboard actions into `onChange(event, data)` and uses `SpinButtonOnChangeData` to report either a committed numeric `data.value` or a committed text `data.displayValue` that still needs consumer parsing.

Labeling and button semantics are more explicit in v9. There is no built-in `label` or `labelPosition` prop on `SpinButton`; use `Field` or your own label composition instead. The increment and decrement buttons are built into the control with default accessible names, and you override those names through the `incrementButton` and `decrementButton` slot props instead of through dedicated top-level aria-label props.

## Architecture and behavior

Treat v9 `SpinButton` as a numeric input primitive. Keep the source of truth in a `number | null`, use `displayValue` only when you want to render formatted text, and update both together inside `onChange`. Button clicks, arrow keys, Home, End, and Page Up or Page Down use the numeric props (`min`, `max`, `step`, `precision`, and the additional v9 `stepPage`) and surface the committed next number through `data.value`.

Typed edits behave differently from step actions. V9 still waits for commit events such as blur, Enter, or a step action before calling `onChange`, but when the committed text cannot be trusted as a number the payload uses `data.displayValue` instead of auto-running a v8-style `onValidate` callback for you. If your migration needs to clamp typed text, reject invalid formats, or preserve prefixes and suffixes, that logic now lives in your own handler.

Use `Field` as the form-field shell when the v8 control used `label`, `labelPosition`, required state, hint text, or validation UI. `Field` owns the visible label, optional horizontal layout through `orientation`, and the `aria-describedby` or `aria-labelledby` relationships for the nested spinbutton while the spinbutton itself remains responsible for bounds, stepping, and formatted value semantics.

## Styling and theming

Use Griffel classes and Fluent v9 design tokens for any migration-specific layout or visual customization. `SpinButton` styling is slot-based: apply root styles through `className` or `root`, adjust the editable text field through `input`, and target the step buttons through `incrementButton` or `decrementButton` slot props. This replaces the v8 `styles`, `upArrowButtonStyles`, `downArrowButtonStyles`, and theme-object customization pattern.

Theme changes move to `FluentProvider`. Avoid copying v8 color values into the migrated control; instead use appearance props plus design tokens in custom Griffel styles so the spinbutton, label, and helper text respond to theme changes together.

## Accessibility

Wrap the control in `Field` when you need a visible label, hint text, or validation message so the spinbutton receives the right `aria-labelledby` and `aria-describedby` relationships. If you intentionally render the control without `Field`, provide an explicit `aria-label` or `aria-labelledby` on `SpinButton`.

V9 `SpinButton` includes increment and decrement buttons with default accessible names of “Increment value” and “Decrement value.” When the generic text is not descriptive enough, replace it with `incrementButtonAriaLabel` and `decrementButtonAriaLabel` equivalents by setting `incrementButton={{ 'aria-label': '...' }}` and `decrementButton={{ 'aria-label': '...' }}`.

When the displayed text is formatted, `displayValue` automatically becomes `aria-valuetext`. Override `aria-valuetext` only if screen readers need wording that differs from the rendered string. The control also sets `aria-valuemin`, `aria-valuemax`, and `aria-valuenow` from the numeric state, so keep the numeric source of truth accurate even when the visible text includes units or currency symbols.

## Unsupported scenarios and known gaps

There is no direct v9 `onValidate` prop. If a v8 migration depended on `onValidate` to clean up free-form text, clamp typed values, or restore suffixes before the value changed, that logic must move into your controlled `onChange` handler by parsing `data.displayValue` and deciding what numeric `value` and rendered `displayValue` to keep.

The v8 `componentRef` instance surface does not carry forward either. A v9 `ref` gives you the input element directly, so helper members like the v8 `ISpinButton.value` accessor do not exist and focus management should use normal DOM focus on the input.

Visible label composition also changes permanently. V9 `SpinButton` has no dedicated `label`, `labelPosition`, or `iconProps` prop, so use `Field` for standard form-field UI and fall back to your own custom label composition when the scenario needs richer content.
