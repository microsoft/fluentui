## Server-Side Rendering

Fluent UI React v9 supports Server-Side Rendering.

### Basic setup

Add `@fluentui/react-components` dependency:

```shell
# Using Yarn
yarn add @fluentui/react-components

# Using NPM
npm install @fluentui/react-components
```

For any setup using SSR, you need to provide a `RendererProvider`, `SSRProvider` and `FluentProvider` in the root of your app. If these providers are not added, there will be issues when hydrating. See the following example:

```tsx
import express from 'express';
import React from 'react';
import ReactDOMServer from 'react-dom/server';
import {
  createDOMRenderer,
  RendererProvider,
  renderToStyleElements,
  FluentProvider,
  webLightTheme,
  SSRProvider,
} from '@fluentui/react-components';

const useExampleStyles = makeStyles({
  root: {
    color: 'red',
  },
});

const ExampleComponent: React.FC = () => {
  const classes = useExampleStyles();

  return <div className={classes.root}>Hello world</div>;
};

const server = express();

server.get('/', (req, res) => {
  const renderer = createDOMRenderer();

  const html = ReactDOMServer.renderToString(
    <RendererProvider renderer={renderer}>
      <SSRProvider>
        <FluentProvider theme={webLightTheme}>
          <ExampleComponent />
        </FluentProvider>
      </SSRProvider>
    </RendererProvider>,
  );

  // Converting Fluent UI styles to style elements. 👇
  const style = ReactDOMServer.renderToStaticMarkup(<>{renderToStyleElements(renderer)}</>);

  res.write(`
  <!DOCTYPE html>
  <html>
    <head>
      ${/* 👇 adding Fluent UI styles elements to output */}
      ${style}
    </head>
    <body>
      <div id="root">${html}</div>
    </body>
  </html>
  `);
  res.end();
});

server.listen(3000, 'localhost');
```

### Build-time ID namespaces

When multiple independently built applications share a document, configure a distinct
[build-time ID namespace](?path=/docs/concepts-developer-advanced-configuration--docs#build-time-id-namespace)
for each Fluent module copy. The Advanced Configuration guide contains complete Webpack, Vite,
and esbuild recipes, including validation and dependency transformation.

Use the **same** `FLUENT_USE_ID_BUILD_PREFIX` input and `__FLUENT_USE_ID_BUILD_PREFIX__` substitution
in both server and client builds. For example, both builds of Calendar should substitute the literal
`"calendar"`; both builds of Chat should substitute `"chat"`. Do not generate separate random values
for the server and client or deploy HTML with assets built for another namespace.

The replacement configuration is identical for the two builds:

```js
const namespace = process.env.FLUENT_USE_ID_BUILD_PREFIX ?? '';
if (namespace && !/^[A-Za-z_][A-Za-z0-9_-]*$/.test(namespace)) {
  throw new Error('Invalid FLUENT_USE_ID_BUILD_PREFIX');
}

const define = {
  __FLUENT_USE_ID_BUILD_PREFIX__: JSON.stringify(namespace),
};
// Pass `define` to esbuild/Vite, or to Webpack's DefinePlugin, for BOTH builds.
```

Ensure that the server build actually transforms Fluent's JavaScript. If the server externalizes
Fluent and imports it directly from `node_modules`, the client bundle's substitution does not
configure that external package. Bundle/transform Fluent on both sides, or use matching outer
`IdPrefixProvider` values without build substitution on both sides.

Keep any `IdPrefixProvider` values identical on the server and client. In React 18 and later, if you
also use React's `identifierPrefix`, pass the same root-specific value to server rendering and
`hydrateRoot`. For example:

```jsx
// Server
const html = renderToString(<App />, { identifierPrefix: 'calendar-instance-a-' });

// Client
hydrateRoot(container, <App />, { identifierPrefix: 'calendar-instance-a-' });
```

The build namespace does not change `SSRProvider` requirements. In particular, React 17 still needs
a request-local `SSRProvider` for matching counters and must render the same tree/order during
hydration. A namespace does not repair counter-order or concurrent-rendering limitations.
Multiple instances of one artifact or apps sharing a Fluent singleton still need per-instance
root/provider prefixes.
