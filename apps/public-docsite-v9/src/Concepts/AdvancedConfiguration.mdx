## Advanced Configuration

### Child Window Rendering

When rendering on the main browser window, many components need access to `window` or `document` for applying styling, listening for events, or measuring things. However it is possible to render to child windows and elements hosted in `iframe` elements.

In these cases, the target element is hosted in a different context, and thus have a different `window` reference. To aid in providing components with the correct instances of `window` or `document`, React context can be used to provide the tree of React components with the correct instance.

#### Configuring rendering

We need to configure a renderer for `makeStyles()` and pass a `targetDocument` to `RendererProvider` & `FluentProvider`:

```jsx
import { createDOMRenderer, FluentProvider, RendererProvider } from '@fluentui/react-components';
import * as React from 'react';

function MyComponent(props) {
  const { children, targetDocument } = props;
  const renderer = React.useMemo(() => createDOMRenderer(targetDocument), [targetDocument]);

  return (
    <RendererProvider renderer={renderer} targetDocument={targetDocument}>
      <FluentProvider targetDocument={targetDocument}>{children}</FluentProvider>
    </RendererProvider>
  );
}
```

You can check complete example at [CodeSandbox](https://codesandbox.io/s/fluentuireact-components-render-into-iframe-l62ke).

### Media Queries Sorting

Fluent UI React v9 uses Griffel as CSS-in-JS to apply styles. To provide deterministic behavior, styles applied by Griffel [are sorted](https://griffel.js.org/react/guides/atomic-css#lvfha-order-of-pseudo-classes), the same applies to media queries. Fluent UI does not provide an opinionated default to sort media queries as the order may vary depending on the specific needs of the application.

To configure the sorting behavior, please pass `compareMediaQueries` function with the same signature as sort functions in e.g. `Array.prototype.sort`.

```js
import { createDOMRenderer } from '@fluentui/react-components';

const mediaQueryOrder = [
  'only screen and (min-width: 1024px)',
  'only screen and (min-width: 1366px)',
  'only screen and (min-width: 1920px)',
];

function sortMediaQueries(a, b) {
  return mediaQueryOrder.indexOf(a) - mediaQueryOrder.indexOf(b);
}

const renderer = createDOMRenderer(document, {
  compareMediaQueries: sortMediaQueries,
});
```

```html
<html>
  <head>
    <style media="only screen and (min-width: 1024px)" data-make-styles-bucket="m"></style>
    <style media="only screen and (min-width: 1366px)" data-make-styles-bucket="m"></style>
    <style media="only screen and (min-width: 1920px)" data-make-styles-bucket="m"></style>
  </head>
</html>
```

For mobile-first methodology, consider using [`sort-css-media-queries`](https://github.com/dutchenkoOleg/sort-css-media-queries):

```js
import { createDOMRenderer } from '@fluentui/react-components';
import sortCSSmq from 'sort-css-media-queries';

const renderer = createDOMRenderer(document, {
  compareMediaQueries: sortCSSmq,
});
```

```html
<html>
  <head>
    <style media="only screen and (min-width: 1px)" data-make-styles-bucket="m"></style>
    <style media="only screen and (min-width: 480px)" data-make-styles-bucket="m"></style>
    <style media="only screen and (min-width: 640px)" data-make-styles-bucket="m"></style>
  </head>
</html>
```

### Content Security Policies (CSP)

To add `nonce` attribute need for [Content Security Policies](https://developer.mozilla.org/en-US/docs/Web/HTTP/CSP), please use `styleElementAttributes` to specify it:

```jsx
import { createDOMRenderer, FluentProvider, RendererProvider } from '@fluentui/react-components';
import * as React from 'react';

function MyComponent(props) {
  const { children } = props;
  const renderer = React.useMemo(
    () => createDOMRenderer(document, { styleElementAttributes: { nonce: 'random' } }),
    [],
  );

  return (
    <RendererProvider renderer={renderer}>
      <FluentProvider>{children}</FluentProvider>
    </RendererProvider>
  );
}
```

### IdPrefixProvider

Having multiple applications using `FluentProvider` on a single web page can cause interop problems when they come from different bundles, more details in [microsoft/fluentui#26496](https://github.com/microsoft/fluentui/pull/26496).

### React 18 and later

**Configure roots first.** Give every independently rendered root a document-wide unique
[`identifierPrefix`](https://react.dev/reference/react-dom/client/createRoot#parameters).
When all roots are configured correctly, a build namespace is not needed to prevent these
Fluent-generated ID collisions. Root prefixing also protects direct React `useId` calls outside Fluent.

```jsx
import * as React from 'react';
import { createRoot } from 'react-dom/client';

const root = createRoot(document.getElementById('root'), {
  identifierPrefix: 'APP1-',
});

root.render(<App />);
```

Multiple roots sharing one ReactDOM client runtime normally share its client ID counter; a second
root alone is not proof of a collision. Independent ReactDOM runtimes and separately rendered SSR
roots are important collision boundaries. Do not rely on a particular counter implementation for
cross-application isolation.
Use simple, distinct root prefixes. Fluent removes colons from React-generated IDs, so prefixes
that differ only by colons are not distinct Fluent namespaces.

### Provider prefixes (all supported React versions)

`IdPrefixProvider` works with all supported React versions, including React 18 and later. Wrap it around
`FluentProvider` so it also prefixes the provider's own theme class and style-tag ID. Use a distinct value
for each independently rendered application instance.
An outer application's provider does not propagate context into a separately created React root;
wrap each root separately.

```jsx
import { IdPrefixProvider, FluentProvider } from '@fluentui/react-components';
import * as React from 'react';

function MyApp() {
  return (
    <IdPrefixProvider value="APP1-">
      <FluentProvider>{/* children */}</FluentProvider>
    </IdPrefixProvider>
  );
}
```

### Build-time ID namespace

Use this **additional safeguard** when you cannot reliably configure every root in independently
built applications. It does not replace per-instance root/provider configuration.

Independently built applications can share a document with a host that cannot configure their React
roots. To namespace Fluent-generated IDs without adding a wrapper, configure your bundler to replace
`__FLUENT_USE_ID_BUILD_PREFIX__` with a string literal in Fluent's JavaScript.
This replacement token is a public build-configuration API, not a runtime export or a browser global.
`FLUENT_USE_ID_BUILD_PREFIX` is the recommended environment variable read by **your build config**;
Fluent does not read it automatically.

The namespace affects both component IDs and `FluentProvider` theme classes/style-tag IDs.
Collisions in provider IDs can otherwise cause theme cross-talk, style reuse, or one application's
unmount removing another application's styles.

#### Interactive reproduction

Open the [FluentProvider ID namespace demonstration](?path=/story/components-fluentprovider--id-namespace).
Each panel contains two independent React/Fluent bundles in the same document, with no root or provider
prefix. Only the protected panel has distinct build namespaces.

Use **Update embedded theme** and **Unmount embedded app**, then inspect the host's computed color,
font-size, and stroke-width tokens. **Reset scenario** reloads the document and its independent runtimes.
The whole scenario uses one iframe to protect Storybook itself; the two apps inside that iframe
are deliberately not isolated from each other.

The controls do not change a build constant at runtime: the two panels load separately built artifacts.
The unconfigured case is a demonstration of an unsafe setup, not supported configuration.

#### Contract

- An absent token or empty string preserves existing generated IDs.
- A non-empty namespace must match `[A-Za-z_][A-Za-z0-9_-]*`. Validate it in your build config;
  development builds also log a `console.error` diagnostic when an invalid substituted value is evaluated. Production bundles
  omit this runtime validation, so build-config validation is required. Values are not silently sanitized.
- The namespace is resolved once when the Fluent module loads. It is not a runtime setting.
- Generated IDs compose as `namespace + "-" + provider prefix + hook prefix + generated suffix`.
  The provider prefix can be empty, but cannot remove the build namespace.
- Non-empty caller-provided IDs remain unchanged. As before, an empty provided ID requests generation.
- The nearest `IdPrefixProvider` wins; nested provider prefixes are not concatenated.
- Server and client must use the same namespace. The exact generated suffix is not part of this contract.
- Opting in intentionally changes generated IDs, theme classes, and style-tag IDs.

For example, namespace `calendar`, provider prefix `dialog-`, and the default hook prefix produce IDs
starting with `calendar-dialog-fui-`. With the same provider prefix, a `FluentProvider` theme class and
its style-tag ID start with `calendar-dialog-fui-FluentProvider`. The remaining suffix is React/version
dependent. The static `fui-FluentProvider` class is unchanged.

#### Webpack

```js
// webpack.config.cjs
const webpack = require('webpack');

const namespace = process.env.FLUENT_USE_ID_BUILD_PREFIX ?? '';
if (namespace && !/^[A-Za-z_][A-Za-z0-9_-]*$/.test(namespace)) {
  throw new Error('Invalid FLUENT_USE_ID_BUILD_PREFIX');
}

module.exports = {
  mode: 'production',
  entry: './src/index.js',
  plugins: [
    new webpack.DefinePlugin({
      __FLUENT_USE_ID_BUILD_PREFIX__: JSON.stringify(namespace),
    }),
  ],
};
```

For example, run `FLUENT_USE_ID_BUILD_PREFIX=calendar webpack`. If you use an env file, load it in your
build config before reading the variable; Webpack does not load it automatically.

#### Vite

```js
// vite.config.js
import { defineConfig, loadEnv } from 'vite';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), 'FLUENT_');
  const namespace = process.env.FLUENT_USE_ID_BUILD_PREFIX ?? env.FLUENT_USE_ID_BUILD_PREFIX ?? '';
  if (namespace && !/^[A-Za-z_][A-Za-z0-9_-]*$/.test(namespace)) {
    throw new Error('Invalid FLUENT_USE_ID_BUILD_PREFIX');
  }

  const define = {
    __FLUENT_USE_ID_BUILD_PREFIX__: JSON.stringify(namespace),
  };

  return {
    define,
    // Include the replacement when dependencies are prebundled during development.
    optimizeDeps: { esbuildOptions: { define } },
  };
});
```

Set `FLUENT_USE_ID_BUILD_PREFIX=calendar` in the environment or the appropriate Vite env file.
Restart Vite with `--force` when changing the namespace to invalidate dependency prebundles.

#### esbuild

```js
// build.mjs
import { build } from 'esbuild';

const namespace = process.env.FLUENT_USE_ID_BUILD_PREFIX ?? '';
if (namespace && !/^[A-Za-z_][A-Za-z0-9_-]*$/.test(namespace)) {
  throw new Error('Invalid FLUENT_USE_ID_BUILD_PREFIX');
}

await build({
  entryPoints: ['src/index.js'],
  bundle: true,
  platform: 'browser',
  outfile: 'dist/app.js',
  define: {
    __FLUENT_USE_ID_BUILD_PREFIX__: JSON.stringify(namespace),
  },
});
```

For example, run `FLUENT_USE_ID_BUILD_PREFIX=calendar node build.mjs`. Load any env file before reading
the variable. `JSON.stringify` is important: define values are JavaScript expressions, not raw strings.
These configurations require no browser `process` shim.

Other bundlers must replace the exact token, including its `typeof` expression, in Fluent dependencies,
not only in application source. Both Fluent ESM and CommonJS output support the token. Do not configure
it while publishing a shared Fluent package: each consumer build supplies its own namespace.

#### Choosing the isolation boundary

| Scenario                                            | Configuration                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Independently built Fluent copies in one document   | Different build namespaces, such as `calendar` and `chat`                                |
| Multiple instances of the same bundle               | A different React root `identifierPrefix` or outer `IdPrefixProvider` per instance       |
| Apps consuming one shared/external Fluent singleton | Root/provider prefixes; one module cannot have a different build value for each consumer |
| IDs generated directly by React outside Fluent      | React root `identifierPrefix`                                                            |
| React 17 server rendering                           | Request-local `SSRProvider`, plus namespaces/root-instance isolation as appropriate      |

Root prefixes, provider prefixes, and the build namespace are additive. React root prefixes also cover
React `useId` calls outside Fluent; the other two only affect Fluent `useId`.

A prebuilt remote cannot be reconfigured by defining the token in an unrelated host bundle.
Neither build namespacing nor provider prefixing rewrites caller-provided IDs, third-party IDs,
static strings, or Griffel identifiers. Repeated instances and shared modules still need the instance
configuration above; a build namespace does not guarantee document-wide uniqueness on its own.

See [Server-Side Rendering](?path=/docs/concepts-developer-server-side-rendering-basic-setup--docs#build-time-id-namespaces)
for matching server/client configuration and externalized server dependencies.
