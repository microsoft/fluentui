### Deviations from the cookbook (each deliberate)

1. **Repo-wide `jest.preset.js` change.** Not "same recipe as react-divider", but required and prescribed by D9. Jest resolves `@fluentui/*` to source via tsconfig path aliases, so any suite rendering a `FluentProvider` now evaluates `import styles from './FluentProvider.module.css'`; without a preset-level mapper those suites fail to _run_. I confirmed this empirically — with the mapper stashed, `HeatMapChart` died at `react-components/react-button/library/src/index.ts:1` (the other worker's module import), proving the per-package pattern does not scale past the first leaf package. I resolved the paths with `require.resolve('./scripts/jest/src/css-modules/…')` rather than `require('@fluentui/scripts-jest')` to keep the preset free of workspace requires (`scripts/jest` pulls in `@fluentui/scripts-monorepo`, which walks the repo on load).

2. **Bug fix in `scripts/jest/src/css-modules/serializer.js`** (Phase 0 infra, authored during the divider pilot). Its `print()` did `val.split(/\s+/).…join(' ')`. pretty-format offers _every_ string in the tree to plugins, not just class attributes — so `FluentProvider-node.test.tsx`, which snapshots a whole multi-line HTML string, had its entire markup collapsed onto one line. Rewritten to mirror `@griffel/jest-serializer`: targeted `String.replace` of `fuicm-…` tokens, one whole-string `trim()`, then a trim of the inside of `class="…"`. Divider's 14 snapshots still pass, so the fix is backward-compatible. Latent bug that would have hit any package snapshotting HTML strings.

3. **`snapshotSerializers` does not merge from a preset** (only `moduleNameMapper`, `setupFiles*`, `transform`, `modulePathIgnorePatterns` do). 85 `jest.config.js` files declare their own and therefore drop the preset's serializer. I patched the two that matter today (`react-provider`, `charts/react-charts` — the only suites whose snapshots contain `fui-FluentProvider`). See open questions.

4. **`react-provider` needed no conformance change.** Unlike react-divider, its `library/src/testing/isConformant.ts` does **not** register `@fluentui/react-conformance-griffel`, so there is no `make-styles-overrides-win` test to disable. Its existing `disabledTests: ['component-handles-classname']` is unrelated and untouched.

5. **`@griffel/core` and `@griffel/react` kept in `dependencies`.** `renderFluentProvider.tsx:8` (`TextDirectionProvider`), `useFluentProvider.ts:3` (`useRenderer_unstable`) and `FluentProvider-node.test.tsx:12-13` still import them. The cookbook's "no `@griffel` import remains" DoD does not apply — react-provider is explicitly a `special`, individually-planned package.

6. **Two `toHaveStyle` assertions removed** from the `dir` tests. They passed only because Griffel _injected_ its atomics into jsdom at runtime; `text-align: start` in a CSS Module has no stylesheet for `getComputedStyle` to read. The `dir` attribute assertions are kept and now carry more weight (logical properties resolve against computed direction). Coverage loss is real and flagged.

### Cascade note for the PR

FluentProvider's base typography/colour moves from _unlayered_ Griffel atomics into `@layer fui.base`. Under D2 that is intended (consumer CSS wins), but the consequence is sharper here than for a leaf component: an **unlayered** third-party reset such as `* { font-family: inherit }` now beats the app's entire base typography, where previously it lost to `.fk6fouc`. Worth calling out explicitly as the highest-blast-radius instance of D2's accepted failure mode.

## Open questions

- `.module.css` is never copied into `lib/` or `lib-commonjs/` by `nx run <pkg>:build`, so the published FluentProvider (and Divider, and Button) would fail to resolve `import styles from './FluentProvider.module.css'` at consumer runtime. D1's per-package CSS pipeline (`dist/styles.css` + generated class-map JS) is still unbuilt. Should this land before more packages convert, or is the VR-storybook-only (source-compiled) path acceptable through Phase 1?
- The repo-wide `snapshotSerializers` entry I added to `jest.preset.js` is silently overridden by the 85 `jest.config.js` files that declare their own. Only `react-provider` and `charts/react-charts` were patched (they are the only suites that snapshot a rendered FluentProvider today). Should the remaining 83 be swept now, or gated on each package's conversion?
- `FluentProvider.test.tsx`'s `toHaveStyle({ textAlign: 'left' | 'right' })` assertions were dropped — jsdom has no stylesheet to resolve `text-align: start` against. Is an RTL VR story an acceptable replacement, or should a computed-style probe against the built storybook be added to the validation harness for global styles?
- `*.styles.raw.js` is still emitted for converted packages (2,268 B for FluentProvider, 2,026 B for Divider) because the raw-styles build step keys on the `*.styles.ts` filename, not on Griffel content. D10 counts its deletion as a metric line item — should the emit be disabled per-package during conversion, or globally in Phase 3?
- `@griffel/core` is now imported only by `FluentProvider-node.test.tsx` inside react-provider, but remains a runtime `dependency`. Drop it to devDependencies now, or leave for the Phase 3 sweep (it is currently reachable only via hoisting)?
- TASK 2 brief said `apps/vr-tests-react-components/src/utilities/*.tsx` 'use Griffel'. They do not — they use inline `style` props only. Does the deferral rationale (stable cross-conversion diffs) still stand, given there is nothing to convert there?
